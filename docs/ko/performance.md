# 성능

DaruDB가 각 언어에서 가장 많이 쓰는 임베디드 데이터베이스와 비교해 얼마나 빨리 읽고 쓰는지, 저장소에 있는 벤치마크로 잰 결과입니다. 모든 데이터베이스에서 같은 객체와 같은 작업을 같은 내구성 설정으로 한 기계에서 실행했습니다.

표는 사이드바에서 고른 언어를 따릅니다. 한 언어의 저장소들은 한 기계에서 차례로 실행했으므로 서로 비교할 수 있지만, 언어가 다른 표는 다른 실행에서 나왔으므로 서로 비교하지 않습니다.

## 무엇을 재는가

객체 100,000개가 든 컬렉션 하나를 씁니다. 객체마다 이름, 고유 인덱스가 걸린 이메일, 인덱스가 걸린 나이, 인덱스 없는 도시와 점수가 있습니다. 행마다 작업을 여러 번 실행한 시간을 작업 수로 나눕니다.

| 작업 | 하는 일 |
| --- | --- |
| 삽입, 동기 커밋마다 객체 하나 | 객체 하나씩 커밋 500번, 커밋마다 디스크를 기다립니다 |
| 삽입, 지연 커밋마다 객체 하나 | 객체 하나씩 커밋 10,000번, 동기화는 나중으로 미룹니다 |
| 트랜잭션 하나로 객체 100,000개 삽입 | 모든 객체를 넣고 커밋까지 합니다 |
| 기본 키로 읽기, 무작위 순서 | 객체 하나 읽기 100,000번 |
| 고유 인덱스로 읽기, 무작위 순서 | 이메일로 객체 하나 읽기 20,000번 |
| 인덱스 값 쿼리, 객체 1,250개 | 나이 하나에 속한 객체 |
| 인덱스 범위 쿼리, 정렬 후 20개 | 나이 다섯 개에 속한 객체를 나이 내림차순, 그다음 키 순으로 정렬한 첫 20개 |
| 인덱스로 개수 세기 | 나이가 40 이상인 객체 |
| 인덱스 없는 쿼리, 객체 1,000개 | 도시 하나에 속한 객체, 열 번 |
| 인덱스 없는 쿼리, 객체 1,000개, 처음 실행 | 그 열 번 가운데 처음 |
| 인덱스 없는 필드로 상위 10개 | 점수가 가장 높은 객체 10개, 열 번 |
| 인덱스 없는 필드로 상위 10개, 처음 실행 | 그 열 번 가운데 처음 |
| 객체 10,000개 읽고 고치기 | 객체마다 읽어서 나이를 바꿔 다시 쓰고, 트랜잭션 하나로 커밋까지 합니다 |
| 객체 10,000개 지우기 | 트랜잭션 하나로 커밋까지 합니다 |

인덱스 없는 쿼리 두 개는 처음 실행을 따로 한 행으로 둡니다. DaruDB는 이런 쿼리를 한 번 실행한 뒤로는 더 빨리 답하기 때문입니다. 검사하거나 정렬하는 필드가 레코드마다 어디 있는지 기억해 두었다가 다음 실행에서 그 자리를 바로 읽습니다. 애플리케이션이 한 번만 실행하는 쿼리라면 처음 실행 행의 시간이 걸립니다.

데이터베이스는 저마다 그 언어의 애플리케이션이 쓰는 방식대로 씁니다. DaruDB는 스키마와 함께 공개 API로, SQLite는 준비한 문장으로 SQL을 쓰고, 키-값 저장소는 애플리케이션이 직접 만들 법한 레코드와 인덱스를 둡니다. 읽은 결과는 모두 필드를 빠짐없이 가진 그 언어의 객체로 만들고, 여러 번 도는 쿼리는 한 번만 준비합니다. 필드 하나를 고칠 때는 SQL이 열 하나만 바꾸듯, 그 언어의 DaruDB 패키지가 허락하면 바뀌는 필드만 씁니다. Node.js와 Python에서는 객체 전체를 다시 쓰려면 그 언어에서 객체를 새로 만들어야 하므로 `update`를 쓰고, Rust와 Dart에서는 타입이 있는 객체를 그대로 다시 씁니다.

Node.js 표에는 Realm에서 옮기려는 애플리케이션을 위해 Realm도 넣었습니다. Realm은 2024년 9월에 공급사가 지원 중단을 알렸고 2025년 9월에 지원이 끝났습니다. 데이터를 옮기는 방법은 [마이그레이션 가이드](./migration/realm.md)에 있습니다. Realm은 키를 정해 주지 않으므로 애플리케이션이 다른 저장소와 같은 키를 객체마다 줍니다. 기본 키 말고는 고유 인덱스가 없어서 이메일에는 일반 인덱스를 걸었고, 준비해 둔 쿼리가 없어서 쿼리 문자열을 호출할 때마다 해석합니다. 고칠 때는 속성 하나만 바꿉니다.

## 공정하게 재는 방법

- **같은 내구성.** 동기 커밋은 디스크가 커밋을 받을 때까지 기다립니다. DaruDB의 기본 커밋, `synchronous = FULL`인 SQLite의 WAL, LMDB의 기본 커밋, redb의 `Durability::Immediate`, Hive의 쓰기 뒤 `flush`, Realm의 커밋이 이에 해당합니다. 지연 커밋은 그 전에 반환합니다. DaruDB의 지연 커밋, `synchronous = NORMAL`, LMDB의 `NO_SYNC`, redb의 `Durability::None`, `flush` 없는 Hive의 쓰기입니다. Realm에는 동기화를 뒤로 미루는 커밋이 없어서 그 행의 Realm 칸은 비어 있습니다. redb의 지연 커밋은 나중에 즉시 커밋을 하기 전까지 아무것도 영속되지 않으므로 다른 것보다 약속이 약합니다.
- **같은 일.** 행마다 찾은 객체의 키와 나이를 찾은 순서대로 해시합니다. 두 데이터베이스의 결과가 다르면 시간을 내지 않고 실행을 실패로 끝냅니다.
- **깨끗한 시작.** 데이터베이스마다 한 번의 실행은 자기 프로세스에서 새 파일로 하고, 데이터베이스가 도는 순서는 실행마다 바뀝니다. 시간은 여러 실행의 중앙값입니다.
- **같은 기계.** 한 언어의 데이터베이스는 한 기계에서 차례로 실행합니다.

데이터베이스가 쓰는 캐시는 기본값 그대로 두되, SQLite만 DaruDB와 같은 32 MiB로 올렸습니다. Hive처럼 모든 객체를 메모리에 두는 데이터베이스는 파일을 건드리지 않고 읽습니다.

표의 결과는 `run-benchmarks` 워크플로가 언어마다 GitHub 호스트 Linux 러너를 하나씩 받아 잰 것입니다. 이 러너들은 쓰기 배리어 없이 디스크를 마운트하므로, 거기서 동기 커밋은 파일 시스템의 일은 기다리지만 디스크 자체의 캐시는 기다리지 않습니다. 러너의 프로세서와 디스크도 실행마다 달라지고, 커밋 행이 그에 따라 가장 크게 움직입니다. Node.js에서 객체 하나를 지연 커밋하는 데 한 실행의 러너에서는 SQLite가 68 µs, DaruDB가 34 µs 걸렸고, 다음 실행의 러너에서는 34 µs와 46 µs가 걸렸습니다. 그 이유는 다음 절에 있습니다. 커밋 행은 한 표 안에서만 비교하세요.

## Realm과 견주면

Realm에서 옮기려는 애플리케이션이라면 Node.js 표를 보면 됩니다. 사이드바에서 Node.js를 고르면 보입니다. DaruDB는 인덱스 없는 필드인 도시 하나로 찾는 쿼리와 고치기를 빼고 모든 행에서 Realm을 앞섭니다. Realm은 속성마다 값을 모아 두므로 도시 값만 읽고, 처음 실행에는 DaruDB 시간의 0.69배가 걸립니다. 열 번을 실행하면 둘이 비슷해집니다. DaruDB는 두 번째 실행부터 처음 실행이 레코드마다 찾아 둔 자리에서 도시를 바로 읽기 때문입니다. Realm은 동기 커밋에 3.8배가 걸리고 지연 커밋은 없으며, 트랜잭션 하나로 객체 100,000개를 넣는 데 5배, 10,000개를 지우는 데 5.3배가 걸립니다. 키로 읽는 데는 4.3배, 이메일로 찾는 데는 9.2배가 걸립니다. 호출할 때마다 쿼리 문자열을 해석하고, 기본 키 말고는 고유 인덱스가 없기 때문입니다. 나이 하나에 속한 객체를 찾는 데는 4.6배, 나이 다섯 개에서 정렬한 첫 20개를 찾는 데는 120배가 걸립니다. 다섯 나이의 객체를 모두 정렬한 다음에야 첫 20개를 고르기 때문입니다. 점수가 가장 높은 객체 10개를 찾는 데는 2.5~3.5배가 걸립니다. 고치기는 둘 다 필드 하나만 바꾸는데, 이번에는 Realm이 DaruDB 시간의 0.82배로 끝냈습니다. 다만 이 행은 실행마다 시간이 크게 달랐습니다. 객체 하나에 Realm은 3.6~41 µs, DaruDB는 4.8~7.7 µs가 걸렸고, 지난 실행에서는 DaruDB가 앞섰습니다.

## DaruDB가 뒤지는 곳과 이유

이번에는 Rust와 Node.js가 AMD EPYC 9V45, Dart가 AMD EPYC 7763, Python이 Intel Xeon Platinum 8573C 프로세서의 러너에서 돌았습니다. DaruDB는 Node.js와 Python에서 대부분의 행을 다른 모든 데이터베이스보다 앞서고, Python에서는 한 행을 빼고 모든 행에서 SQLite를 앞섭니다. Dart에서는 트랜잭션 하나로 객체 100,000개를 넣을 때, 인덱스를 쓰는 읽기와 쿼리, 개수 세기, 고치기에서 앞서고, 모든 객체를 메모리에 두는 Hive가 키로 읽기와 인덱스 없는 쿼리에서 앞섭니다. Rust에서는 대부분의 행에서 LMDB가 앞서고, 나이 인덱스를 쓰는 쿼리와 인덱스 없는 쿼리의 처음 실행에서는 redb와 SQLite도 앞섭니다. DaruDB가 앞서지 못하는 행과 그 이유는 아래와 같습니다.

- **객체 하나를 지연 커밋할 때.** LMDB가 실행되는 모든 언어에서 DaruDB 시간의 0.35~0.53배로 앞서고, Rust에서는 redb가 0.71배, Dart에서는 SQLite가 0.77배로 앞섭니다. Linux에서 DaruDB의 커밋은 절반쯤을 커널에서 보냅니다. 시스템 호출이 열네 번쯤인데, 열한 개 남짓한 페이지를 쓰는 쓰기가 열 번이고, 나머지 네 번은 쓰기 잠금을 얻고 놓는 호출과 다른 쓰기 프로세스와 읽기 프로세스가 있는지 확인하는 호출입니다. 프로세스끼리 파일 잠금만으로 조율하기 때문입니다. LMDB는 쓰기 일곱 번이면 되고, 프로세스를 공유 메모리의 뮤텍스로 조율합니다. DaruDB는 이 방식을 쓰지 않습니다. 뮤텍스를 쥔 프로세스가 죽으면 나머지가 멈춰 설 수 있기 때문입니다. SQLite의 지연 커밋은 커밋만으로 끝나지 않습니다. 로그가 천 페이지 찰 때마다 체크포인트를 하며 로그와 파일을 동기화하는데, 대부분의 러너에서 SQLite의 지연 커밋은 시간의 3분의 2 이상을 이 동기화를 기다리며 보냈습니다. EPYC 7763 러너는 이 동기화를 더 빨리 끝내고, 러너 기종 가운데 가장 오래된 그 프로세서는 아무것도 기다리지 않는 DaruDB의 커밋을 가장 느리게 처리합니다. 이번에 그 러너에서 돈 것은 Dart뿐이고, 다른 기종의 러너에서 돈 Rust, Node.js, Python에서는 DaruDB의 지연 커밋이 SQLite의 절반 안팎이나 그보다 짧게 걸렸습니다.
- **동기 커밋**은 다른 어떤 행보다 실행마다 크게 흔들립니다. 이번에는 Dart에서 SQLite가 DaruDB 시간의 0.86배로 앞서고, Node.js와 Python에서는 DaruDB가 앞서며, Rust에서는 DaruDB와 redb가 비슷합니다. 러너에서 동기 커밋은 대부분 파일 시스템의 일입니다. DaruDB는 커밋의 페이지를 빈 페이지가 있는 곳, 곧 파일 곳곳에 흩어 쓰는데, SQLite는 로그 끝에 이어서 씁니다. 디스크만 따로 잰 시험에서 EPYC 7763 러너는 파일 곳곳에 흩어 쓴 12쪽을 동기화하는 데, 같은 12쪽을 한곳에 이어 쓴 것보다 세 배가 걸렸습니다.
- **Rust에서 읽기와 인덱스를 쓰는 쿼리.** 키로 객체를 찾는 데 LMDB는 DaruDB 시간의 0.77배, redb는 0.91배가 걸리고, 이메일로 찾는 데 LMDB는 0.84배가 걸립니다. 나이 인덱스를 쓰는 쿼리는 LMDB, redb, SQLite가 0.52~0.91배에 끝냅니다. DaruDB의 조회는 루트 아래로 거치는 페이지마다 페이지 캐시에서 잠금을 잡고 참조 수를 세어 페이지를 찾고, 노드 안에서 키를 바이트로 비교해 탐색한 다음, 필드마다 id를 붙인 레코드를 구조체로 디코딩합니다. 페이지 캐시에서 찾는 일이 조회에서 차지하는 몫은 이 x86 프로세서에서 Apple 프로세서보다 큽니다. LMDB는 파일을 메모리에 매핑해 읽으므로 찾아볼 캐시가 없고, redb는 기본 키를 정수로 비교하며, 둘 다 필드를 정해진 자리에 둔 직접 짠 레코드를 읽습니다. DaruDB가 파일을 매핑하지 않는 까닭은 매핑한 바이트를 다른 프로세스가 읽는 도중에 바꿀 수 있고, 매핑은 암호화와 함께 쓸 수 없기 때문입니다. 정렬한 범위 읽기는 비용이 더 듭니다. 이 쿼리는 나이 내림차순, 그다음 키 순으로 정렬하므로 DaruDB는 나이 인덱스를 거꾸로 훑으며 나이마다 객체를 붙잡아 두었다가 키 순으로 내놓는데, 키-값 저장소용으로 짠 반복문은 나이를 하나씩 차례로 요청합니다. Apple M1 Max에서는 정렬한 범위 읽기를 빼고 이 행들 모두 DaruDB가 LMDB를 앞섰습니다.
- **Dart에서 키로 읽을 때**는 Hive가 DaruDB 시간의 0.81배로 앞섭니다. Hive는 박스의 모든 객체를 메모리에 두고 쥐고 있는 객체를 그대로 내주지만, DaruDB는 페이지 캐시를 거쳐 트리에서 레코드를 찾고 그 레코드로 객체를 만듭니다.
- **인덱스 없는 쿼리.** Rust의 LMDB가 2.8~7배, Dart의 Hive가 1.5~2.9배 빨리 훑고, Node.js의 Realm은 도시 하나의 객체를 처음 실행에서는 더 빨리, 열 번 실행에서는 비슷하게 찾습니다. SQLite와 redb는 처음 실행에서만 앞섭니다. SQLite는 Rust, Node.js, Dart에서 DaruDB 시간의 0.78~0.92배, Python에서는 두 쿼리 가운데 하나에서 0.97배가 걸리고, redb는 Rust에서 0.89배와 0.96배가 걸립니다. 열 번을 실행하면 DaruDB가 둘 다 앞서고, 둘은 DaruDB 시간의 1.03~1.51배가 걸립니다. 키-값 저장소용으로 직접 짠 레코드는 나이와 점수를 정해진 자리에 두므로 그 바이트만 읽고 돌려줄 객체만 디코딩합니다. Realm은 속성마다 값을 모아 두므로 도시 값만 읽고, SQLite의 레코드는 맨 앞에 열의 타입을 늘어놓으므로 한 열을 찾을 때 앞선 값을 읽지 않고 크기만 더합니다. DaruDB의 레코드는 필드마다 id와 타입을 붙여 이름을 바꿔도 비용이 없고, 믿을 수 없는 파일에서 읽은 내용을 엔진이 검사할 수 있게 합니다. 그래서 처음 훑을 때는 레코드마다 검사할 필드 앞의 필드를 하나씩 건너뜁니다. 찾은 자리는 기억해 두므로 두 번째 실행부터는 그 자리에서 바로 읽습니다.
- **Node.js에서 고유 인덱스로 찾을 때**는 SQLite가 DaruDB 시간의 0.85배로 앞섭니다. 인덱스에서 이메일의 항목을 찾고 그 키로 객체를 다시 찾는 두 번의 조회가 들고, 레코드로 JavaScript 객체를 만드는 데 그 시간의 5분의 1이 듭니다.
- **Dart에서 객체 10,000개를 지울 때**는 SQLite가 DaruDB 시간의 0.84배로 앞섭니다. 같은 기종의 러너에서 돈 지난 실행에서는 0.93배였고, 다른 언어에서는 DaruDB가 앞섭니다. DaruDB의 커밋은 앞선 커밋이 비운 페이지, 곧 파일 곳곳에 흩어진 자리에 페이지를 쓰므로, 로그 끝에 이어 쓰는 SQLite보다 쓰기 호출이 훨씬 많습니다.
- **Rust와 Node.js의 고치기**에서는 Rust에서 SQLite가 DaruDB 시간의 0.93배, Node.js에서 Realm이 0.82배가 걸렸지만, 이번 실행에서는 이 행의 시간이 실행마다 크게 달랐습니다. 객체 하나를 고치는 데 DaruDB는 Rust에서 4.6~8.7 µs, Node.js에서 4.8~7.7 µs가 걸렸고, Realm은 3.6~41 µs가 걸렸습니다. 이만큼 흩어진 행은 공유 러너에서 한 번 실행할 때 흔들리는 범위 안입니다.

## 직접 실행하기

하네스는 저장소의 [`bench/`](https://github.com/jooy2/darudb/tree/main/bench)에 있고, README에 모든 설정을 적었습니다. `run-benchmarks` 워크플로가 GitHub 호스트 러너에서 하네스를 돌리고, 이 페이지에 실을 결과로 풀 리퀘스트를 엽니다.

```bash
cd bench/rust && cargo build --release && cd ../..
node bench/run.mjs rust --runs 5 --out bench/results/rust.json
```
