# 엔진의 구조

이 페이지는 Rust로 작성한 DaruDB 엔진이 어떤 계층으로 이뤄졌는지, 바인딩이 엔진에 무엇을 넘기는지, 파일을 어떻게 읽고 캐시하는지, 어떤 스레드를 띄우는지 설명합니다.

## 엔진 하나와 얇은 바인딩

엔진은 Rust 크레이트 `darudb`입니다. Node.js 패키지는 같은 엔진 위에 얹은 바인딩이고, Dart 패키지도 같은 방식으로 만들 계획입니다. 바인딩은 자기 언어의 값과 엔진의 값을 서로 바꿔 줄 뿐, 파일에 관해서는 아무것도 정하지 않습니다. 객체를 스키마와 대조하고, 인덱스를 객체와 맞춰 두고, 쿼리를 파싱하고 실행 계획을 세워 실행하고, 스키마를 마이그레이션하고, 실패마다 오류 코드를 붙이는 일은 모두 엔진이 합니다. 그래서 한 언어에서 쓴 파일을 다른 언어에서 읽어도 똑같이 읽히고, 오류도 어느 언어에서나 같은 `code`를 갖습니다.

### Rust 크레이트의 위치

`darudb` 크레이트는 바인딩 뒤에 숨은 내부 부품이 아니라 엔진 그 자체입니다. Rust 프로그램은 이 크레이트를 의존성으로 추가해 중간 단계 없이 바로 호출하며, 크레이트는 세 가지를 제공합니다.

- **객체 계층.** 스키마와 타입이 있는 객체의 컬렉션, 인덱스, 쿼리, 마이그레이션입니다. 모든 언어에 있습니다. [컬렉션과 객체](../guide/objects.md)에서 다룹니다.
- **저장 커널.** 객체 계층의 바탕이 되는, 이름 붙은 트리에 바이트 키와 바이트 값을 담는 계층입니다. Rust에만 있습니다. [저장 커널](./storage-kernel.md)에서 다룹니다.
- **바인딩이 쓰는 호출.** 버전 단계마다 멈추는 마이그레이션으로 데이터베이스를 여는 호출, 레코드로 주고받는 객체, IR로 주고받는 쿼리입니다. [바인딩 만들기](./bindings.md)에서 설명합니다.

## 계층

각 계층은 자기보다 아래 계층만 씁니다. 그래서 계층 하나를 따로 읽고, 테스트하고, 갈아 끼울 수 있습니다. 아래에서부터 차례로 보면 다음과 같습니다.

| 계층 | 모듈 | 맡은 일 |
| --- | --- | --- |
| 파일 형식 | `format` | 파일의 모든 바이트가 뜻하는 바입니다. 헤더, 페이지, 노드, 포인터, 커밋 레코드와 객체 계층이 키, 레코드, 스키마, 쿼리를 바이트로 나타내는 방식을 정합니다. 입출력 없이 바이트만 다루는 함수로 이뤄집니다. |
| 암호화 | `crypto` | 페이지 암호화와 복호화, 데이터 키 감싸기, 비밀번호에서 키 만들기, 커밋 레코드 인증을 맡습니다. 여기도 입출력이 없습니다. |
| 운영체제 | `sys` | Rust 표준 라이브러리에 없는 시스템 호출입니다. 바이트 범위 잠금, 기존 파일을 덮어쓰지 않는 이름 바꾸기, Windows에서 파일을 식별하는 방법을 다룹니다. `unsafe` 코드가 있는 유일한 모듈입니다. |
| 저장소 | `storage` | 바이트가 디스크에 닿는 방식입니다. 오프셋을 지정한 읽기와 쓰기, 페이지마다 검사하고 암호화하고 복호화하는 페이저, 페이지 캐시, 새 파일 만들기를 맡습니다. |
| B+트리 | `btree` | 페이지 위에 쌓은 쓰기 시 복사 B+트리입니다. 조회, 양방향 순회, 변경, 커밋할 때 바뀐 노드를 바이트로 바꾸는 일을 합니다. |
| 빈 공간 | `space` | 쓰기 트랜잭션이 쓸 수 있는 페이지와 돌려줄 페이지를 관리하고, 더는 아무 읽기도 닿지 않는 페이지를 회수합니다. |
| 잠금 | `lock` | 운영체제의 바이트 범위 잠금으로 프로세스 사이를 조율합니다. |
| 인스턴스 | `instance` | 프로세스 안에서 열린 파일마다 하나씩 있는 공유 상태입니다. 파일 핸들, 이 프로세스가 아는 마지막 커밋, 쓰기 관문, 스냅샷 목록, 페이지 캐시, 백그라운드 스레드를 둡니다. |
| 트랜잭션 | `txn` | 읽기·쓰기 트랜잭션과 커밋, 복구를 맡습니다. |
| 객체와 쿼리 | `schema`, `query` | 스키마와 마이그레이션, 인덱스와 함께 쓰는 객체, 그리고 쿼리입니다. 쿼리는 IR과 빌더, 쿼리 언어, 인덱스 고르기, 실행으로 이뤄집니다. |
| 도구 | `tools` | 무결성 검사, 백업, 압축, 되살리기입니다. |
| 공개 API | `database`, `options`, `error` | `Database`, `OpenOptions`, `Error`입니다. 크레이트는 이들을 아래 계층의 공개 타입과 함께 내보냅니다. |

엔진이 저장하는 것은 객체까지 모두 저장 커널의 트리에 들어갑니다. 컬렉션 하나는 객체의 기본 키를 인코딩한 값에서 그 객체의 레코드로 가는 트리 하나이고, 인덱스도 각각 트리 하나입니다. 이 트리들의 이름은 NUL 바이트로 시작하는데, 커널이 엔진 몫으로 남겨 둔 이름이라 프로그램이 만드는 트리와 겹치지 않습니다. 그래서 객체를 커밋하는 일은 곧 트리를 커밋하는 일이고, 내구성과 복구와 잠금도 그대로 따라옵니다. 배치는 [파일 형식](./file-format.md)에 있습니다.

## 바인딩이 엔진에 넘기는 것

다른 언어에서 Rust를 부를 때마다 인자와 결과를 변환해야 합니다. 실제로는 엔진이 하는 일보다 이 변환 비용이 바인딩의 속도를 정하는 경우가 많습니다. 그래서 바인딩은 객체를 필드 하나씩 넘기지 않고, 엔진이 정한 형식의 바이트 버퍼를 넘깁니다.

- **레코드.** 객체는 레코드로 오갑니다. 레코드는 번호로 구분한 필드의 모음이고, 필드마다 태그와 값이 있습니다. 쓸 객체 여러 개는 버퍼 하나에 담아 넘기고, 쿼리가 찾은 객체도 버퍼 하나에 담겨 돌아옵니다.
- **쿼리 IR.** 바인딩의 쿼리 빌더로 만든 쿼리는 필터, 정렬, 오프셋, 개수 제한을 담은 버퍼 하나로 넘어갑니다. 쿼리 언어로 쓴 문자열은 엔진이 같은 IR로 파싱하므로, 모든 언어가 파서 하나를 함께 씁니다.
- **스키마.** 선언한 스키마는 데이터베이스를 열 때 한 번, 파일이 스키마를 저장하는 형식 그대로 넘어갑니다.

엔진은 받은 버퍼를 저장하기 전에 모두 검사합니다. 레코드는 스키마와, 쿼리는 쿼리가 가리키는 컬렉션과 대조합니다. 바인딩이 무엇을 보내든 스키마가 허용하지 않는 것은 쓰이지 않습니다. 형식과 그 형식을 받는 호출은 [바인딩 만들기](./bindings.md)에 있습니다.

## 파일 읽고 쓰기

엔진은 파일을 읽고 쓸 때마다 오프셋을 지정합니다. 유닉스 계열에서는 `pread`와 `pwrite`를, Windows에서는 오프셋을 받는 읽기·쓰기 호출을 씁니다. 커밋은 이어진 페이지 묶음을 호출 한 번으로 쓰며, 시스템에 `pwritev`가 있으면 그것을 씁니다. 파일을 메모리에 매핑하지는 않습니다.

파일을 매핑하면 페이지를 복사하지 않고 그 자리에서 읽을 수 있습니다. 그런데도 매핑을 쓰지 않는 이유는 두 가지입니다.

- **다른 프로세스가 파일을 바꿀 수 있습니다.** 파일 하나를 여러 프로세스가 함께 쓰고, 그중 어느 프로세스든 언제라도 커밋해 페이지를 쓰거나 파일을 줄일 수 있습니다. 매핑한 바이트는 Rust 규칙상 바뀌지 않아야 할 참조 아래에서 바뀔 수 있으므로, 안전한 코드는 그런 참조를 쥘 수 없습니다. 오프셋을 지정한 읽기는 다른 누구도 바꾸지 않는 사본이고, 쓰기 전에 검사값과 대조합니다.
- **암호화.** 암호화한 파일의 페이지는 읽기 전에 복호화해야 합니다. 매핑에는 암호문이 들어 있을 테니 평문을 담을 사본이 어차피 따로 필요합니다.

그 대가로 매핑이 아껴 줄 복사를 치러야 하므로, 성능 목표는 매핑 없이 달성해야 합니다. 페이지 캐시가 그 복사를 드물게 만듭니다.

## 페이지 캐시

프로세스는 읽은 페이지를 캐시에 둡니다. 캐시는 열린 파일마다 하나이고, 그 프로세스에서 같은 파일을 연 핸들이 모두 함께 씁니다. 페이지는 처음 읽을 때 한 번만 검사값과 대조하고, 암호화한 파일이면 그때 복호화합니다. 캐시에서 다시 읽을 때는 파일을 읽지도 검사하지도 않습니다.

- **키는 페이지 번호와 검사값입니다.** 읽는 쪽은 자신을 그 페이지로 이끈 포인터에서 기대할 검사값을 늘 알고 있으므로, 같은 페이지의 옛 버전이 캐시에 남아 있어도 맞지 않습니다. 그래서 다른 프로세스가 커밋해도 무효화할 것이 없습니다. 더는 맞는 데가 없는 항목은 차례가 되면 밀려납니다.
- **크기는 바이트로 셉니다.** 파일마다 기본 32 MiB이고, 적어도 16페이지는 둡니다. 페이지를 읽는 만큼만 차고, 먼저 들어온 페이지부터 내보냅니다. 크기는 Rust에서는 `OpenOptions::cache_size`로, Node.js에서는 `cacheSize` 옵션으로 정합니다. 한 프로세스에서 파일을 처음 연 핸들의 설정을 모든 핸들이 따릅니다.
- **트리 노드만 둡니다.** 캐시에 든 노드는 키마다 앞쪽 몇 바이트를 페이지 옆에 따로 두어서, 검색할 때 그 바이트가 같은 키만 끝까지 읽습니다. 이 부분은 메모리에만 있고 캐시 크기에 포함됩니다. 따로 페이지를 차지하는 큰 값은 캐시하지 않고 읽을 때마다 파일에서 읽습니다.
- **커밋이 캐시를 채웁니다.** 커밋이 쓴 노드는 캐시에 들어가므로 다음 트랜잭션은 그 노드를 캐시에서 찾습니다.

## 백그라운드 스레드

엔진은 두 종류의 스레드를 띄우며, 둘 다 할 일이 있을 때만 돕니다. 디버거나 프로파일러에서 이름으로 구별할 수 있습니다.

- **`darudb-sync`.** 디스크 기록을 기다리는 지연 커밋이 있는 파일마다 하나씩 뜹니다. 마지막 동기화 뒤에 첫 지연 커밋이 생기면 이 스레드가 뜨고, 시간 제한이 지나면 `sync`처럼 그동안의 지연 커밋을 디스크와 동기화합니다. 다른 프로세스가 동기화하지 않은 채 남긴 커밋도 지켜보다가, 커밋 레코드에 적힌 구간이 시간 제한을 넘기도록 그대로면 대신 동기화합니다. 그 프로세스가 죽었을 수 있기 때문입니다. 지연 커밋이 모두 동기화되면 스레드도 끝납니다. 파일을 약한 참조로만 쥐므로 데이터베이스를 열린 채로 붙잡아 두지 않습니다.
- **`darudb-keeper`.** 프로세스마다 하나입니다. 한 커밋을 보던 마지막 읽기 트랜잭션이 끝나도 프로세스는 그 스냅샷 잠금을 20밀리초 동안 놓지 않습니다. 그래야 곧이어 시작하는 읽기 트랜잭션이 적은 비용으로 그 잠금에 합류합니다. 이 스레드가 그렇게 남겨 둔 잠금을 풀며, 10초 동안 할 일이 없으면 끝납니다.

시스템이 두 스레드 중 하나를 띄우지 못해도 잃는 것은 없습니다. 시간 제한이 지난 뒤에 하는 지연 커밋은 그 자리에서 동기화되고, 남겨 둔 잠금은 프로세스가 더 새 커밋을 읽거나, 쓰기 트랜잭션을 시작하거나, 파일을 닫을 때 풀립니다. 자세한 내용은 [커밋과 복구](./commits-and-recovery.md)와 [잠금](./locking.md)에 있습니다.
