이 페이지 콘텐츠

파일 형식 ​

이 페이지는 DaruDB 데이터베이스 파일이 페이지와 헤더, 세 커밋 슬롯, 모든 페이지를 검사하는 포인터로 어떻게 배치되는지, 형식 버전은 어떻게 매기는지 요약합니다.

모든 오프셋과 필드는 저장소의 design/file-format.md에 명세돼 있습니다. 이 문서는 지금 빌드가 쓰는 형식 버전 6과, 함께 읽고 쓰는 버전 5를 설명합니다.

페이지 ​

데이터베이스는 파일 하나이고, 파일은 같은 크기의 페이지로 나뉩니다.

  • 페이지 크기는 4096부터 65536바이트까지의 2의 거듭제곱입니다. 파일을 만들 때 정해 헤더에 기록합니다. 기본값은 4096입니다. 벤치마크에서 페이지가 크면 순회와 개수 세기는 빨라졌지만, 페이지 캐시보다 큰 파일에서 조회가 느려졌고 작은 커밋도 느려졌습니다. 캐시에 없는 페이지를 읽을 때마다 페이지 전체를 읽고 검사하고, 커밋은 페이지 단위로 쓰기 때문입니다. 주로 순회하는 애플리케이션이라면 파일을 만들 때 더 큰 페이지를 고를 수 있습니다.
  • 페이지 번호는 64비트입니다. 0번 페이지가 헤더이고, 나머지 페이지는 B+트리의 노드이거나 큰 값의 일부입니다.
  • 운영체제의 메모리 페이지 크기와는 상관이 없습니다. 엔진은 파일을 매핑하지 않으므로 메모리 페이지 크기를 가정하지 않습니다. 메모리 페이지가 16 KB로 바뀐 Android에서 이 점이 중요합니다.
  • 커밋마다 파일의 페이지 수를 기록합니다. 그 수를 넘어선 페이지는 그 커밋에 속하지 않습니다.
  • 파일은 2^62번째 바이트에 닿지 않습니다. 잠금용 바이트가 거기서 시작합니다(잠금).

헤더 ​

0번 페이지는 키를 포함해 나머지를 어떻게 읽을지 알려 주는 곳이라 암호화하지 않습니다. 앞쪽 2048바이트는 512바이트 섹터 단위로 배치합니다. 그래야 섹터가 512바이트인 디스크에서도 커밋 슬롯 하나를 쓰다가 다른 슬롯을 망가뜨리지 않습니다.

바이트내용
0~63고정 필드. 매직 바이트 \x89DaruDB\n, 형식 버전, 페이지 크기, 무작위 16바이트로 된 파일 ID, 암호 방식, 그리고 이 모두의 검사값입니다. 파일을 만들 때 쓰고, 형식 버전을 올릴 때만 다시 씁니다.
64선택 바이트
128~191올릴 고정 필드. 형식 버전을 올릴 때 새 고정 필드를 먼저 여기에 씁니다
512~2047512바이트짜리 커밋 슬롯 세 개

매직의 첫 바이트는 ASCII 범위 밖이라 파일이 텍스트로 오인되지 않고, 여덟 번째 비트를 떼어 내는 전송도 잡아냅니다. 마지막 바이트인 줄바꿈은 줄바꿈 문자를 바꾸는 전송을 잡아냅니다.

선택 바이트 ​

커밋할 때마다 다시 쓰는 1바이트입니다. 비트 두 개는 게시된 커밋, 곧 새로 시작하는 읽기가 보는 커밋이 든 슬롯을 가리킵니다. 비트 하나는 미동기화 비트로, 그 커밋이 지연 커밋이라 아직 내구성이 없을 수 있을 때 켜집니다. 1바이트 쓰기는 원자적이므로, 읽는 쪽이나 정전 뒤의 복구는 옛 값과 새 값 중 하나만 봅니다. 그래서 읽는 쪽은 잠금 없이 게시된 커밋을 찾습니다.

커밋 슬롯 세 개 ​

슬롯마다 커밋 레코드가 하나 들어 있거나 비어 있습니다. 레코드에는 커밋의 트랜잭션 ID, 레코드를 쓸 때 내구성이 보장된 가장 새 커밋의 트랜잭션 ID, 페이지 수, 아래에서 설명할 엔진 트리 세 개의 루트, 암호화한 파일이면 키 블록과 MAC, 지연 커밋이면 미동기화 구간이 열린 시각과 그 구간이 쓴 페이지 수, 그리고 슬롯 번호를 섞어 계산한 검사값이 들어갑니다. 슬롯 번호를 섞으므로 다른 슬롯에 잘못 쓴 레코드는 검사에서 걸립니다.

슬롯은 셋이 최소입니다. 언제든 슬롯 하나에는 게시된 커밋이, 하나에는 내구성이 보장된 커밋이 있습니다. 지연 커밋이 디스크 기록을 기다리는 동안 이 둘은 다릅니다. 그리고 쓰는 쪽은 지금 쓰는 레코드를 둘 세 번째 자리가 필요합니다. 그래서 새 레코드는 읽는 쪽이나 복구가 아직 필요로 할 수 있는 레코드를 덮어쓰지 않습니다. 쓰는 쪽이 슬롯을 고르는 방식은 커밋과 복구에 있습니다.

페이지의 틀 ​

0번을 뺀 모든 페이지는 같은 틀을 씁니다.

바이트내용
0~23암호화한 페이지의 논스. 평문 파일에서는 0
24~55페이지 헤더. 종류(리프, 브랜치, 오버플로), 높이, 항목 수, 페이지를 쓴 커밋의 트랜잭션 ID, 속한 트리의 ID, 오버플로 페이지라면 묶음 안의 위치
56부터 끝 16바이트 앞까지내용
끝 16바이트페이지의 검사값
  • 모든 페이지가 논스 자리를 비워 둡니다. 암호화 여부와 상관없습니다. 그래야 같은 연산으로 만든 트리가 암호화 여부와 상관없이 같은 모양이 되고, 테스트 하나로 두 경우를 모두 확인할 수 있습니다. 대가는 페이지마다 24바이트로, 4096바이트 페이지에서 0.6%입니다.
  • 페이지 헤더는 부모가 이미 아는 내용을 되풀이합니다. 덕분에 페이지 하나만 보고도 무엇인지 알 수 있습니다. 무결성 검사는 이 헤더를 부모의 기대와 비교하고, 되살리기는 부모를 잃은 페이지를 트리에 되돌려 놓을 때 씁니다.

포인터와 검사값 ​

페이지가 다른 페이지를 가리킬 때도, 헤더가 트리의 루트를 가리킬 때도 32바이트 포인터를 씁니다. 포인터에는 페이지 번호(8바이트), 그 페이지를 쓴 커밋의 트랜잭션 ID(8바이트), 페이지의 검사값(16바이트)이 들어 있습니다.

  • 검사값은 평문 파일에서는 페이지 번호와 페이지 바이트의 XXH3-128 해시이고, 암호화한 파일에서는 페이지의 인증 태그입니다(암호화). 페이지 번호를 섞으므로 엉뚱한 자리에 쓴 페이지는 자기 검사값부터 맞지 않습니다.
  • 모든 페이지는 안의 내용을 사용하기 전에 자신을 가리킨 포인터와 대조합니다. 검사값이 맞아야 하고, 헤더의 트랜잭션 ID도 맞아야 합니다. 이 대조로 디스크에서 손상된 페이지, 끝내 디스크에 닿지 못한 쓰기가 남긴 옛 페이지, 엉뚱한 자리에 쓴 페이지를 잡아냅니다. 대조에 실패한 페이지는 읽지 않고 CORRUPTED로 알립니다.
  • 트랜잭션 ID 덕분에 복구가 가볍습니다. 크래시 뒤에 복구는 마지막으로 내구성이 보장된 커밋 이후에 쓴 페이지만 검사합니다. 어느 자식이 그런 페이지인지는 포인터의 ID가 알려 주므로 나머지는 읽지 않습니다.

XXH3-128은 매번 모든 페이지를 검사해도 부담이 적을 만큼 빠르고, 128비트라 페이지가 수십억 개여도 우연히 맞을 가능성은 무시할 만합니다. 암호학적 해시는 아니며 그럴 필요도 없습니다. 이 해시는 사고를 잡아내는 용도이고, 의도적인 변조는 암호화한 파일의 태그가 막습니다.

트리 ​

트리마다 ID가 있고 트리의 모든 페이지가 그 ID를 지닙니다. 트리 ID는 다시 쓰지 않으므로, 되살리기는 파일의 전체 이력에 걸쳐 어떤 페이지가 어느 트리 것이었는지 가릴 수 있습니다.

ID트리
1카탈로그. 트리마다 이름과 ID, 루트, 항목 수
2빈 페이지 트리. 이제 아무것도 닿지 않아 쓰는 쪽이 쓸 수 있는 페이지 묶음
3보류 트리. 이전 커밋만 닿는 페이지를, 그 페이지를 더는 쓰지 않게 된 커밋별로 묶어 둔 것. 읽는 쪽도 복구도 필요로 하지 않게 될 때까지 둡니다
4~15엔진 몫으로 남겨 둠
16 이상위 계층의 트리. 저장 커널의 트리와 객체 계층의 컬렉션, 인덱스
  • 리프는 내용 앞쪽의 2바이트 오프셋 배열로 항목을 키 순서대로 가리킵니다. 브랜치에는 자식 포인터와 자식 사이를 가르는 키가 있습니다.
  • 형식 6에서는 항목의 길이를 가변 길이 정수로 적습니다. 키 길이와, 값의 길이를 적거나 값이 오버플로 묶음에 있다고 알리는 태그입니다. 키가 128바이트보다 짧고 값이 64바이트보다 짧으면 각각 1바이트를 씁니다. 형식 5는 여기에 5바이트를 썼습니다. 인덱스 항목은 짧아서 리프 하나에 항목이 5분의 1쯤 더 들어갑니다. 리프의 페이지 종류가 어느 배치인지 알려 주므로, 형식 5에서 올린 파일에는 두 배치의 리프가 섞여 있습니다.
  • 리프는 이웃과 연결하지 않습니다. 쓰기 시 복사 트리에서 이웃을 가리키는 링크를 두면 리프를 복사할 때마다 이웃도 다시 써야 합니다. 그래서 순회는 루트에서 내려온 경로를 기억합니다.
  • 큰 값은 이어진 페이지로 된 오버플로 묶음에 들어가고, 항목에는 44바이트짜리 참조가 남습니다. 참조에는 묶음에 속한 페이지들의 검사값을 다시 해시한 값이 들어 있습니다.
  • 키는 부호 없는 바이트 순서로만 정렬합니다. 키는 페이지의 4분의 1보다 조금 작은 길이까지입니다. 그래서 노드 하나에 항목 네 개가 늘 들어가고, 넘친 노드는 언제나 둘로 나눌 수 있습니다.
  • 카탈로그가 트리마다 항목 수를 기록하므로 트리 전체의 개수를 세는 데 드는 비용이 없습니다.

트리에 담긴 객체 ​

객체 계층은 모든 것을 이름이 0x00 바이트로 시작하는 트리에 둡니다. 카탈로그가 엔진 몫으로 남겨 둔 이름입니다. \0meta에는 저장된 스키마와 컬렉션의 자동 증가 카운터가 있고, 컬렉션마다 기본 키를 인코딩한 값에서 객체의 레코드로 가는 트리가 있으며, 인덱스도 각각 트리 하나입니다. 키는 값의 순서대로 바이트가 정렬되게 인코딩하고, 레코드에는 필드 이름 대신 필드 ID가 들어가므로 필드 이름을 바꿔도 다시 쓰는 레코드가 없습니다. 저장된 스키마에는 이 인코딩을 위한 형식 번호가 따로 있습니다. 명세는 design/objects.md에 있습니다.

파일 읽기 ​

엔진은 파일에서 읽은 것을 모두 믿을 수 없는 입력으로 다룹니다. 사용하기 전에 매직, 형식 버전, 고정 필드의 검사값, 페이지 크기와 암호 방식, 선택 바이트의 예약 비트, 사용하려는 커밋 레코드를 확인합니다. 페이지마다 파일 안에 있고 페이지 수보다 작은 번호인지, 검사값과 트랜잭션 ID, 종류, 높이, 트리가 포인터와 부모가 기대하는 대로인지, 페이지 안의 오프셋과 길이가 모두 페이지 안에 머무는지도 확인합니다. 손상된 파일은 오류로 끝나고 프로그램을 멈추게 하지 않습니다. 손상은 CORRUPTED, DaruDB 데이터베이스가 아닌 파일은 NOT_A_DATABASE입니다.

브랜치 아래의 모든 키가 구분 키 사이에 있는지처럼 여러 페이지에 걸친 확인은 매번 읽을 때가 아니라 무결성 검사에서 합니다(도구).

형식 버전 ​

헤더의 형식 버전은 디스크에 있는 모든 것의 배치를 가리키며, 쓰는 내용이 조금이라도 바뀌면 버전도 바뀝니다.

  • 지금 빌드는 형식 버전 6을 쓰고, 버전 5도 읽고 씁니다. 더 오래됐든 더 새것이든 그 밖의 버전 파일은 UNSUPPORTED_FORMAT_VERSION으로 거부하고, 오류에 찾은 버전을 적습니다. 헤더의 앞 16바이트는 버전 1부터 배치가 같으므로, 어느 빌드든 DaruDB 파일인지와 그 버전은 알아볼 수 있습니다.
  • 첫 릴리스의 형식은 버전 5입니다. 모든 패키지의 1.0이 첫 릴리스입니다. 버전 1부터 4까지는 개발 단계를 벗어난 적이 없으므로, 그 빌드들이 만든 파일은 업그레이드하지 않고 거부합니다.
  • 버전 6은 리프 항목의 길이를 가변 길이 정수로 적습니다. 인덱스 14개를 둔 객체 40만 개짜리 파일이 버전 5보다 페이지를 8% 덜 씁니다. 126 MiB 대 138 MiB이고, 압축하면 110 MiB 대 119 MiB입니다. 읽기와 쓰기 속도는 벤치마크의 오차인 2% 안에서 버전 5와 같았습니다.
  • 이후의 형식 버전은 모두 바로 앞 버전에서 옮겨 오는 마이그레이션과 함께 나옵니다. 버전 5 파일을 열면, 다른 프로세스가 그 파일을 열고 있지 않은 한 버전 6으로 올립니다. OpenOptions::upgrade_format(false)upgradeFormat: falseupgradeFormat: falseupgrade_format=False로 끌 수 있습니다.

버전을 올릴 때는 헤더만 다시 씁니다. 파일에 있던 리프는 버전 6도 읽는 배치 그대로 있다가, 쓰기가 바꿀 때 새 배치로 다시 쓰입니다. 압축은 새 배치로 공간이 줄어드는 트리를 다시 씁니다. 버전 5만 아는 릴리스는 올린 파일을 열지 못합니다. 그래서 그런 릴리스로 되돌아갈 수 있는 애플리케이션은 올리기를 끄고, 되돌아갈 일이 없어지면 Database::upgrade_formatdb.upgradeFormat()db.upgradeFormat()db.upgrade_format()을 부릅니다. 올리기를 끄면 새 파일도 버전 5로 만듭니다. 이 호출은 파일을 혼자 써야 하므로, 다른 프로세스가 파일을 열고 있으면 BUSY로 실패합니다.

고정 필드의 검사값이 버전까지 덮고, 원자적인 쓰기는 1바이트뿐이라 둘을 한 번에 바꿀 수 없습니다. 그래서 새 고정 필드를 128~191바이트에 먼저 쓰고, 그다음 버전 바이트, 마지막으로 새 검사값을 쓰며, 쓸 때마다 동기화합니다. 어디서 끊겨도 파일은 두 버전 중 하나로 열립니다. 버전 바이트까지 썼다면 맞지 않는 검사값은 먼저 써 둔 사본이 보증하고, 다음에 파일을 혼자 여는 프로세스가 검사값을 마저 씁니다.
