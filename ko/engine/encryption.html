암호화 ​

이 페이지는 DaruDB가 데이터베이스 파일을 암호화하고 인증하는 방법, 곧 페이지 암호 방식과 그 선택 기준, 데이터 키를 키나 비밀번호로 감싸는 방식, 커밋 레코드의 MAC, 암호화한 파일에서도 보이는 것을 설명합니다.

명세는 저장소의 design/file-format.md 가운데 "Encryption" 절입니다. 암호화한 데이터베이스를 만들고 열고 키를 바꾸는 방법은 암호화에서 다룹니다.

암호화하는 범위 ​

키나 비밀번호로 만든 데이터베이스는 평생 암호화된 채로 남습니다. 헤더를 뺀 모든 페이지, 그러니까 모든 키와 값, 트리 이름이 암호화됩니다. 모든 페이지는 인증도 받고, 헤더에 있는 커밋 레코드도 하나하나 인증받습니다. 그래서 바이트 하나라도 바뀌면 그대로 읽지 않고 CORRUPTED로 알립니다.

평문 데이터베이스는 평문으로 남습니다. 그 자리에서 암호화할 수는 없고, 키나 비밀번호로 새 데이터베이스를 만들어 데이터를 옮겨야 합니다.

페이지 ​

페이지는 파일의 데이터 키 아래에서 인증 암호로 암호화합니다.

  • 논스는 무작위 24바이트이고, 페이지를 쓸 때마다 새로 뽑습니다. 모든 페이지가 비워 두는 페이지의 앞 24바이트에 저장합니다.
  • 연관 데이터는 페이지 번호입니다. 암호문을 파일 안의 그 자리에 묶어 둡니다.
  • 인증 태그 16바이트가 페이지의 검사값입니다. 페이지 끝과, 그 페이지를 가리키는 포인터에 함께 저장합니다.

태그가 부모에도 있으므로, 파일에 쓸 수 있는 사람이라도 같은 페이지의 예전 버전을 되돌려 놓을 수 없습니다. 예전 버전이 제대로 암호화된 것이라도 태그가 부모에 기록된 것과 맞지 않습니다. 큰 값의 묶음 검사값은 그 페이지들의 태그를 해시한 값이라, 큰 값의 페이지도 같은 보호를 받습니다.

암호 방식 고르기 ​

파일은 XAES-256-GCM과 XChaCha20-Poly1305 중 하나를 씁니다. 둘 다 24바이트 논스를 받고 16바이트 태그를 내므로 페이지 배치는 어느 쪽이든 같습니다.

새로 만드는 암호화 파일은, 그 파일을 만드는 기기의 프로세서에 AES 명령어와 캐리 없는 곱셈 명령어가 있으면 XAES-256-GCM을, 없으면 XChaCha20-Poly1305를 씁니다. 각자 맞는 프로세서에서는 상대보다 몇 배 빠르기 때문입니다. Apple 실리콘 기기 한 대에서 4 KiB 페이지를 암호화하는 속도는 XAES-256-GCM이 초당 약 3.0 GB, XChaCha20-Poly1305가 0.7 GB였고, 소프트웨어 구현만 쓰면 0.13 GB와 0.32 GB로 순서가 뒤집혔습니다. 오래된 32비트 ARM 휴대폰이나 일부 소형 ARM 보드에는 이 명령어가 없는데, 그런 기기에서도 이 선택 덕분에 파일이 빠릅니다.

애플리케이션은 암호 방식을 고르지 않습니다. 헤더에 암호 방식을 기록하고 파일은 평생 그 방식을 쓰며, 어느 기기든 두 방식의 파일을 모두 엽니다. 다만 프로세서가 그 방식에 맞지 않으면 더 느릴 뿐입니다.

무작위 192비트 논스는 키 하나로 페이지를 몇 번을 쓰든 안전합니다. 일반 AES-256-GCM은 논스가 96비트라서, 키 하나로 페이지를 2^32번쯤 쓰고 나면 무작위 논스가 안전하지 않습니다. 카운터를 논스로 쓰려 해도, 쓰는 프로세스가 여럿이고 크래시가 날 수 있으면 값을 겹치지 않게 유지하기 어렵습니다. XAES-256-GCM은 24바이트 논스의 앞쪽 절반으로 AES-256-GCM 키를 새로 만들어 이 문제를 풉니다.

데이터 키와 키 블록 ​

페이지는 데이터 키 아래에서 암호화합니다. 데이터 키는 파일을 만들 때 생성한 무작위 32바이트입니다. 데이터 키는 감싼 형태로 키 블록에 들어 있고, 모든 커밋 레코드가 키 블록을 하나씩 지닙니다.

  • 데이터 키를 감싸는 키는 호출하는 쪽이 준 32바이트 키이거나, 호출하는 쪽이 준 비밀번호를 키 블록에 저장된 솔트와 비용으로 Argon2id 해시한 값입니다.
  • 감쌀 때는 XChaCha20-Poly1305를 씁니다. 연관 데이터는 파일 ID라서, 키 블록을 다른 파일에 복사해도 거기서는 풀리지 않습니다.
  • 파일을 열 때는 검사값이 맞는 커밋 레코드의 키 블록마다 가장 새 것부터 키나 비밀번호를 대 보고, 처음 풀리는 것을 씁니다. 레코드들은 데이터 키 하나를 공유하므로 어느 레코드로 풀든 상관없습니다. 키나 비밀번호가 틀리면 모든 감싸기 태그가 맞지 않아 WRONG_KEY로 실패합니다. 암호화한 파일을 키나 비밀번호 없이 열면 KEY_REQUIRED로, 평문 파일을 키나 비밀번호로 열면 INVALID_ARGUMENT로 실패합니다.

키나 비밀번호 바꾸기 ​

키나 비밀번호를 바꾸면 새 키 블록을 쓸 뿐 페이지는 다시 암호화하지 않으므로, 파일 크기와 상관없이 걸리는 시간이 같습니다. 새 키 블록을 담은 동기 커밋을 하고, 옛 키 블록이 남은 슬롯이 없어질 때까지 빈 동기 커밋을 이어 합니다. 그사이에 다른 커밋이 없으면 모두 세 번입니다. 모든 커밋은 직전 커밋의 키 블록을 복사하므로, 새 키 블록이 이렇게 나머지 슬롯에 퍼집니다. 그동안에는 옛 키로도 파일이 열리지만, 호출이 반환된 뒤에는 열리지 않습니다. 호출은 Rust에서는 Database::set_key와 Database::set_password, Node.js에서는 setKey와 setPassword입니다.

데이터 키 자체는 파일이 살아 있는 동안 바뀌지 않습니다. 백업과 되살리기도 새 파일에 옛 파일의 키 블록을 그대로 쓰므로 데이터 키가 같고, 원본을 여는 키나 비밀번호로 사본도 열립니다.

비밀번호 ​

비밀번호는 Argon2id로 키가 됩니다. Argon2id는 메모리를 많이 쓰도록 만든 해시라서, 그래픽 처리 장치로 비밀번호를 대량으로 추측하는 데 비용이 많이 듭니다. 기본 비용은 메모리 19 MiB, 반복 2회, 레인 1개로, OWASP 비밀번호 저장 지침에 나오는 Argon2id 설정 가운데 가장 낮은 것입니다. 요즘 컴퓨터에서 수십 밀리초가 걸립니다. 이 값을 정한 것은 메모리입니다. 모바일 앱 확장은 프로세스 전체에 이 정도 메모리밖에 쓰지 못할 수 있습니다.

비용은 키 블록마다 저장하므로, 애플리케이션은 파일을 만들거나 비밀번호를 바꿀 때 형식을 바꾸지 않고도 더 높은 비용을 요청할 수 있습니다. Rust에서는 OpenOptions::password_hashing, Node.js에서는 passwordHashing입니다. 파일을 열 때는 늘 그 파일을 만들 때의 비용이 듭니다. 메모리 1 GiB, 반복 1024회, 레인 64개를 넘는 비용을 요구하는 키 블록은 해시하기 전에 CORRUPTED로 거부합니다. 해시가 메모리를 한꺼번에 잡기 때문입니다.

커밋 레코드 ​

헤더는 평문이고, 페이지의 태그는 페이지 자신뿐 아니라 부모에도 평문으로 들어 있습니다. 그러니 커밋 레코드에 별도의 키가 없다면, 파일에 쓸 수 있는 사람은 누구나 이미 있는 페이지로 커밋 레코드를 조립할 수 있습니다. 한 커밋의 카탈로그에 다른 커밋의 빈 페이지 트리를 붙이는 식입니다. 키를 가진 누구도 그런 상태를 커밋한 적이 없고, 그 트리들은 어느 페이지가 사용 중인지에 대해 서로 다른 말을 하므로, 다음 커밋이 사용 중인 페이지를 덮어쓰게 됩니다.

그래서 암호화한 파일의 레코드마다 MAC이 붙습니다. 데이터 키에서 끌어낸 키로 계산하는, 출력 16바이트짜리 키 있는 BLAKE2b이며, 파일 ID와 슬롯 번호, 레코드의 필드와 키 블록을 덮습니다. 복구는 MAC이 맞지 않는 레코드를 택하지 않고, 다른 프로세스가 쓴 레코드를 읽는 프로세스도 MAC을 확인합니다. BLAKE2b는 Argon2id 때문에 이미 빌드에 들어 있고, MAC을 따로 두면 레코드가 페이지 암호 방식에 묶이지 않습니다.

그래도 보이는 것 ​

헤더 페이지는 평문이라, 암호화한 파일에서도 페이지 크기, 파일 ID, 암호 방식, 트랜잭션 ID, 페이지 수와 그에 따른 파일 크기, 트리 루트의 페이지 번호가 보입니다. 페이지 안의 내용은 모두 암호화돼 있습니다.

파일 전체나 헤더 페이지만을 그 파일의 예전 사본으로 바꿔치기하면 파일 안에서는 알아챌 수 없습니다. 예전 레코드도 진짜이기 때문입니다. 이를 알아채야 하는 애플리케이션은 가장 새 트랜잭션 ID를 다른 곳에 보관해야 합니다. Rust에서는 ReadTransaction::commit_id로 읽습니다.

메모리 속의 키 ​

엔진은 키를 버릴 때 지워지는 버퍼에 두고, 암호 구현도 자기가 가진 키 사본을 지웁니다. 그러면 키가 메모리에 머무는 시간은 줄지만, 컴파일러나 운영체제가 만든 사본까지 막지는 못합니다. Node.js 패키지는 받은 키나 비밀번호를 자기 버퍼에 복사하고, 엔진이 호출 시점에 자기 사본을 만들면 그 버퍼를 0으로 채웁니다. JavaScript 문자열로 넘긴 비밀번호는 가비지 컬렉터가 회수할 때까지 메모리에 남으므로, 지울 수 있게 하려면 Uint8Array로 넘기세요.

키는 운영체제의 키 저장소처럼 잃어버리지 않을 곳에 보관하세요. 키가 없으면 데이터를 읽을 수 없습니다.
